# Security boundary

This reference binds to loopback and enforces expected Host/Origin, local CSRF, bounded JSON input, fixed static routes, no-store responses and CSP. Demo never loads remote SDK code or collects card details. Sandbox loads approved hosted code only after explicit configuration; it has no live mode. These safeguards support local development and do not provide customer authentication or production order authorization.

Keep `API_KEY` on the backend. The publishable key is browser-facing; a client secret is sensitive, payment-scoped session material and should reach only the authorized browser over HTTPS in production. Do not put secrets in public config, local/browser storage, URLs, logs, analytics, errors, tests, archives or version control. The starter stores only an opaque order ID in sessionStorage, discards redirect queries/fragments immediately, and keeps API client secrets in memory. Do not store or log cardholder data, PAN or CVV. Use the hosted payment UI and review the resulting PCI boundary.

Local state lives outside the source, with restrictive directory/file permissions, a process ownership lock, and a namespace for mode/API origin/profile. Back it up privately and preserve financial identities. Never remove an active lock or rewrite/reset state to recover an uncertain action. After an abrupt stop, follow the [stale-lock procedure](integration.md#local-state-recovery-and-capacity), which requires stopping/verifying all owners, backing up the directory, removing only the confirmed stale `.lock`, and preserving `state.json`. The same guide explains the 16 MiB capacity limit and safe refusal of oversized updates. The reference is single-process, local state: production needs transactional durability, concurrent ownership controls, retention, recovery, and restricted access to identifiers.

Before sandbox use an administrator must verify the actual provider test mode, endpoint, routing, merchant/profile and credentials. Shared hostnames and merchant key scope can cross environment/profile boundaries. Separate production/test credentials and persistent state; reject order/payment/profile mismatches. Never retry a timed-out create or confirmation blindly. Use authenticated status retrieval and operator reconciliation.

For a public customer backend, add authenticated sessions, order ownership authorization, HTTPS, appropriate CSRF protections, rate limits, reviewed CSP/CORS, durable one-time fulfilment, verified webhooks, redacted observability and operational key rotation. Avoid broad CORS or CSP relaxation to make hosted integration appear successful. Document actual origin/frame/network requirements against the served SDK first. Secrets belong in the customer's approved runtime secret manager, never in the ZIP or image.

The release script copies only reviewed allowlisted files, rejects symlink inputs and existing release outputs, and excludes environment/state/dependency/cache paths. Review all allowed files before release: allowlisting cannot detect a secret deliberately inserted into a source file or template. Checksums detect byte changes; distribution authenticity requires a trusted delivery channel. No remote SDK is bundled or authenticated by the archive checksum.

Outgoing webhooks have no accepting route until the deployed signing/secret contract is verified. Unknown paths are rejected; no unsigned fallback is available. See [webhooks](webhooks.md). Report suspected vulnerabilities privately to the platform maintainer and follow the applicable upstream security policy; do not include real credentials or sensitive payment payloads in reports.
