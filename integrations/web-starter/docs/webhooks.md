# Outgoing webhook verification is blocked

This starter exposes **no accepting webhook endpoint**. Unknown webhook routes are rejected. The actual deployed outgoing signing configuration, secret distribution and revision/feature parity have not been verified. Do not add an unsigned receiver or assume that a valid redirect establishes payment success.

The 2026-09-30 source/config audit of the sibling Hyperswitch snapshot (`2025.06.18.0-hotfix1`, v1) found a candidate native contract: hex-encoded HMAC-SHA512 over exact serialized JSON bytes, header `X-Webhook-Signature-512`, and profile `payment_response_hash_key`. Signing can be omitted when that key is absent. Relevant source references are `crates/router/src/core/webhooks/types.rs`, `src/core/webhooks/outgoing.rs`, `src/core/admin.rs`, and `src/lib.rs`. Checked-in `webhooks.outgoing_enabled` settings establish source defaults, not deployed values. This evidence comes from the platform readiness audit `06-webhook-readiness.md`; no authenticated runtime inspection or webhook delivery was performed for this package.

Native event names in that snapshot are snake_case, including `payment_succeeded`, `payment_failed`, `payment_processing`, `payment_cancelled`, `refund_succeeded` and `refund_failed`. Do not assume dotted names or a `payment.created`/`refund.created` event. Optional Stripe compatibility can change the payload contract, so confirm the selected deployed mode before building a receiver. This package does not implement refunds or certify event coverage for a connector.

Before a receiver is enabled, establish deployed revision and native/compatibility payload mode, exact raw-body signature encoding, configured profile secret and its secure distribution/rotation, enabled delivery/profile URL, event identity, retry schedule, scheduler/Postgres/Redis operation, retry retention and receiver authentication/network policy. Confirm with safe fixtures and separately approved sandbox evidence, including invalid/missing signature, wrong secret, duplicate, delayed retry, timeout/non-2xx and out-of-order delivery.

A reviewed receiver must verify the signature over **raw received bytes before parsing**, compare in constant time, reject unknown/missing/invalid signatures, and persist authenticated event identity durably before prompt 2xx acceptance. Reconcile the expected payment through the authenticated API and match order, amount, currency and profile before one-time fulfilment. Persist deduplication and handle reordered statuses, retries, poison events and reconciliation alerts.

The audited sender retries a saved signed body and original timestamp; retry attempt IDs differ from the body event ID. A narrow current-time window alone can reject legitimate delayed retries. Agree a replay/retention policy compatible with actual deployed retry timing rather than inventing a timestamp header or exactly-once guarantee. Missing deployed evidence is a platform/merchant provisioning blocker outside package delivery.
